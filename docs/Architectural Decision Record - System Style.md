# ADR-001: System Style

## Статус

**Accepted**

## Дата

06.04.2026

## Проєкт

Family Wallet — веб-застосунок для управління сімейним бюджетом

## Контекст

Система «Family Wallet» має забезпечувати надійне ведення сімейного бюджету: облік доходів і витрат, розподіл коштів між членами родини та категоризацію транзакцій. Фінансові операції вимагають точності та цілісності даних — не можна допустити ситуацію, коли транзакція записалася частково або баланс розрахований некоректно.

**Технічні обмеження:**

- Команда розробки складається з 4 осіб, досвід роботи з розподіленими системами обмежений.
- Термін реалізації MVP — приблизно 14 тижнів.
- Бюджет на інфраструктуру мінімальний: використовуються Cloudflare Pages (frontend, безкоштовний тір), Render.com (backend, безкоштовний тір — 512 MB RAM, 0.1 CPU) та MongoDB Atlas (безкоштовний тір).
- Технологічний стек вже зафіксований: Vue 3 (frontend), FastAPI (backend), MongoDB Atlas (база даних).

**Ключові вимоги:**

- Висока швидкість розробки (Time-to-Market) для випуску MVP.
- Гарантована узгодженість фінансових даних (Data Consistency) — баланс сім'ї має бути точним у кожний момент часу.
- Простота підтримки та розгортання (Maintainability, Deployability).
- Можливість паралельної роботи членів команди без блокувань.

## Рішення

Ми обираємо **Модульну Монолітну архітектуру (Modular Monolith)**. Система буде побудована як єдиний розгортаний юніт, але з чітким розділенням коду на логічні модулі: **Auth**, **Wallets**, **Transactions**, **Categories**, **Reports**.

## Обґрунтування (Rationale)

**Обраний стиль:** Modular Monolith

**Аргумент 1 "За" — Узгодженість фінансових даних:**
Family Wallet працює з грошовими операціями, де точність є критичною. Моноліт дозволяє виконувати операції з балансом та транзакціями в рамках єдиного процесу, без ризиків мережевих збоїв між сервісами. Це забезпечує Data Consistency без необхідності впроваджувати складні патерни розподілених транзакцій (Saga pattern), які є надмірними для нашого масштабу.

**Аргумент 2 "За" — Мінімальний інфраструктурний Overhead:**
Backend пакується в один Docker-контейнер (розгортається на Render.com), а frontend — у статичний бандл (розгортається на Cloudflare Pages). Це мінімізує витрати на DevOps: не потрібно налаштовувати Service Discovery, API Gateway, Message Broker або оркестрацію контейнерів. Такий підхід означає лише 1 інстанс backend замість потенційних 5–7 для мікросервісної архітектури, що критично при обмеженому бюджеті.

**Аргумент 3 "За" — Швидкість розробки при обмежених ресурсах команди:**
Команда з 4 студентів може ефективно працювати з єдиною кодовою базою: спільне середовище розробки, один процес деплою, просте налагодження (debugging). Час, який ми заощадимо на інфраструктурі, буде інвестовано в реалізацію бізнес-функцій.

**Перспектива:**
Код буде розділений на логічні модулі (Auth, Wallets, Transactions, Categories, Reports) з чіткими межами відповідальності. Якщо проєкт масштабується (наприклад, модуль Reports потребуватиме окремого масштабування через важкі обчислення), ми зможемо винести його в окремий мікросервіс, змінивши лише Infrastructure Layer, без переписування бізнес-логіки.

## Наслідки (Consequences)

**Позитивні:**

- Легке налагодження (debugging): весь стек-трейс доступний в одному процесі, що прискорює пошук помилок у фінансових розрахунках.
- Висока швидкість обміну даними між модулями (виклик функцій у пам'яті замість мережевих запитів), що зменшує Latency.
- Єдина точка входу для автентифікації та авторизації (JWT middleware застосовується глобально).
- Простий CI/CD pipeline: один Dockerfile для backend (Render.com) та статичний бандл для frontend (Cloudflare Pages) — мінімальний ризик помилок при розгортанні.

**Негативні:**

- Неможливо масштабувати окремі модулі незалежно. Якщо модуль Reports створює високе навантаження, доведеться масштабувати весь backend.
- Оновлення одного модуля потребує перезапуску всієї системи, що може спричинити короткочасний downtime.
- Ризик поступового розмивання меж між модулями (coupling growth), якщо команда не дотримуватиметься дисципліни розділення коду.
- Єдина точка відмови: помилка в одному модулі (наприклад, некоректна обробка в Reports) може вплинути на працездатність усієї системи.

## Альтернативи

**Microservices Architecture:**
Відхилено через надмірну складність інфраструктури для проєкту з командою з 4 студентів. Налаштування Service Discovery, API Gateway, міжсервісної комунікації (gRPC/RabbitMQ) та розподіленого логування забрало б понад 40% часу розробки. Крім того, Eventual Consistency між сервісами створює ризик некоректних фінансових розрахунків, що неприпустимо для бюджетного додатку.

**Serverless (FaaS):**
Відхилено через складність локального тестування та налагодження, а також через Cold Start проблему, яка створює непередбачувану Latency для користувача. Додатково, обрані платформи (Render.com для backend, Cloudflare Pages для frontend) не є Serverless-платформами, що потребувало б зміни інфраструктурних рішень.
