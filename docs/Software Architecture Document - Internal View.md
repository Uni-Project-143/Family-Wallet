# SAD-001: Internal View

## Статус

**Accepted**

## Дата

06.04.2026

## Проєкт

Family Wallet — веб-застосунок для управління сімейним бюджетом

## Description

### 1. Аналіз структури даних та логіки (Input)

**Складність бізнес-правил: Низька–Середня.**
Проєкт Family Wallet включає типові CRUD-операції (створення транзакцій, управління категоріями, облік членів родини), доповнені базовою бізнес-логікою:
- Валідація фінансових операцій (сума транзакції має бути додатною, категорія — існуючою).
- Розрахунок балансу гаманця на основі суми всіх транзакцій.
- Фільтрація та агрегація транзакцій для формування звітів (за період, категорією, членом родини).

Бізнес-логіка не вимагає складних доменних моделей чи довгих ланцюгів правил — це переважно операції збереження, читання та агрегації з простою валідацією.

**Джерела даних:**
Основне сховище — MongoDB Atlas (NoSQL). Зміна СУБД на цьому етапі не планується, оскільки MongoDB добре підходить для документо-орієнтованої структури фінансових записів та забезпечує гнучкість схеми.

**Фреймворк:**
FastAPI (Python) — легкий фреймворк, що природно підтримує Layered-підхід через свою модульну структуру роутерів (APIRouter), залежностей (Depends) та Pydantic-моделей для валідації.

**Чи планується зміна джерел даних?**
Ні. MongoDB Atlas є фінальним вибором для MVP та прогнозованого масштабу проєкту.

### 2. Вибір патерну

**Обраний патерн: Layered Architecture (Багатошарова архітектура)**

**Чому Layered, а не Clean/Onion:**
- Бізнес-логіка Family Wallet не є достатньо складною, щоб виправдати додатковий Overhead Clean Architecture (додаткові шари абстракцій, інтерфейси портів та адаптерів).
- Команда з 4 студентів має обмежений досвід, і Layered Architecture є найбільш інтуїтивним та зрозумілим патерном, що зменшує когнітивне навантаження.
- FastAPI природно «схиляє» до Layered-підходу: роутери → сервіси → репозиторії — це вже фактично три шари.
- Зміна СУБД не планується, тому інверсія залежностей через інтерфейси (ключова перевага Clean Architecture) не дає практичної вигоди на цьому етапі.
- Для CRUD-домінантної системи Layered забезпечує оптимальний баланс між структурованістю коду та швидкістю розробки.

### 3. Визначення відповідальності шарів (Layers)

| Шар | Назва в проєкті | Відповідальність та компоненти |
|-----|-----------------|-------------------------------|
| **Presentation Layer** | `api/` (routers) | Приймає HTTP-запити. Містить FastAPI роутери (endpoints), визначає URL-маршрути, HTTP-методи та коди відповідей. Використовує Pydantic-схеми (DTO) для валідації вхідних даних та серіалізації відповідей. Містить middleware для JWT-авторизації, CORS та обробки помилок. **Не містить бізнес-логіки.** |
| **Business Logic Layer** | `services/` | Реалізує сценарії використання (Use Cases): «Додати транзакцію», «Розрахувати баланс», «Отримати звіт за період». Оркеструє виклики до Data Access Layer. Виконує валідацію бізнес-правил (наприклад, перевірка, що користувач є членом гаманця). **Не знає про HTTP-запити та відповіді.** |
| **Data Access Layer** | `repositories/` | Інкапсулює всі операції з MongoDB через Motor (async driver). Містить методи для CRUD-операцій над колекціями: `users`, `wallets`, `transactions`, `categories`. Повертає дані у вигляді Python-словників або Pydantic-моделей. **Не містить бізнес-логіки.** |
| **Models Layer** | `models/` | Описує структури даних (Entities), які зберігаються в MongoDB: User, Wallet, Transaction, Category. Визначає поля, типи та значення за замовчуванням. |
| **Schemas Layer** | `schemas/` (DTO) | Контракти даних для входу/виходу API. Pydantic-моделі для валідації request body (наприклад, `CreateTransactionSchema`) та формування response (наприклад, `TransactionResponseSchema`). Відокремлюють внутрішню структуру БД від зовнішнього API. |
| **Config Layer** | `config/` | Налаштування підключення до MongoDB, JWT-параметри (secret key, algorithm, expiration), змінні середовища. Завантажуються через `python-dotenv`. |

### 4. Схема залежностей

```
┌─────────────────────────────────────────────────┐
│              Presentation Layer                  │
│         (api/routers + middleware)                │
│                                                  │
│   Приймає HTTP → Валідує через Schemas (DTO)     │
│   → Викликає Services → Повертає Response        │
└──────────────────────┬──────────────────────────┘
                       │ залежить від
                       ▼
┌─────────────────────────────────────────────────┐
│           Business Logic Layer                   │
│               (services/)                        │
│                                                  │
│   Реалізує Use Cases → Викликає Repositories     │
│   → Застосовує бізнес-правила                    │
└──────────────────────┬──────────────────────────┘
                       │ залежить від
                       ▼
┌─────────────────────────────────────────────────┐
│            Data Access Layer                     │
│             (repositories/)                      │
│                                                  │
│   CRUD-операції з MongoDB через Motor            │
│   → Використовує Models для структури даних      │
└──────────────────────┬──────────────────────────┘
                       │ залежить від
                       ▼
┌─────────────────────────────────────────────────┐
│              Database (MongoDB)                   │
│                                                  │
│   Колекції: users, wallets, transactions,        │
│   categories, wallet_members                     │
└─────────────────────────────────────────────────┘
```

**Напрямок залежностей (зверху вниз):**

```
api/routers  ──────►  services/  ──────►  repositories/  ──────►  MongoDB
     │                    │                     │
     ▼                    ▼                     ▼
  schemas/            schemas/              models/
   (DTO)               (DTO)              (Entities)
```

**Ключові правила залежностей:**

1. **Presentation → Business Logic:** Роутери викликають сервіси, але сервіси **ніколи** не імпортують код з роутерів.
2. **Business Logic → Data Access:** Сервіси викликають репозиторії, але репозиторії **ніколи** не імпортують код з сервісів.
3. **Schemas використовуються на рівнях API та Services** для передачі даних між шарами у структурованому вигляді.
4. **Models використовуються на рівні Repositories** для опису структури документів MongoDB.
5. **Config доступний з будь-якого шару** — це cross-cutting concern (налаштування середовища).

Ця структура гарантує, що зміна логіки відображення (наприклад, додавання нового endpoint) не вплине на бізнес-правила, а зміна способу збереження даних (наприклад, оптимізація запитів до MongoDB) не потребує правок у роутерах.
