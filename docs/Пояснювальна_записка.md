## 1. Архітектурний опис

### 1.1. Обґрунтування вибору технологій

Технологічний стек фіксувався під три ключові обмеження проєкту: **команда з 4 студентів**,
**термін MVP ≈ 14 тижнів** та **мінімальний (безкоштовний) інфраструктурний бюджет**.

| Шар | Технологія | Обґрунтування вибору |
|-----|-----------|----------------------|
| **Frontend** | Vue 3 (Composition API), Vue Router, Vite, Axios | Низький поріг входу та швидка розробка SPA; Composition API дає перевикористовувану логіку через composables; Vite забезпечує миттєвий hot-reload і компактний production-бандл, придатний для статичного хостингу. |
| **Backend** | FastAPI + Uvicorn (Python 3.12), Pydantic v2 | Асинхронний фреймворк з нативною валідацією через Pydantic та автогенерацією OpenAPI/Swagger; структура `APIRouter → Depends` природно лягає на багатошарову архітектуру. |
| **База даних** | MongoDB Atlas (драйвер Motor, async) | Документо-орієнтована модель ідеально пасує гнучкій структурі фінансових записів та подій; безкоштовний хмарний тір без адміністрування СУБД. |
| **Безпека** | PyJWT, passlib[bcrypt], cryptography | JWT у httpOnly Secure Cookie (захист від XSS); bcrypt-хешування паролів; шифрування персональних токенів Monobank у сховищі. |
| **Real-time** | WebSocket (FastAPI) + Firebase Cloud Messaging | Миттєве оновлення сімейної стрічки та модальних запитів; push-сповіщення на пристрої. |
| **Зовнішня інтеграція** | Monobank Open API (webhooks) | Транзакції надходять автоматично — користувач не вводить їх вручну. |
| **Інфраструктура** | Docker, Docker Compose, GitHub Actions | Один контейнер backend + статичний бандл frontend; відтворюване середовище; CI/CD без ручних кроків. |
| **Хостинг** | Render.com (backend), Cloudflare Pages (frontend) | Безкоштовні тіри, автодеплой із гілки `production`. |

### 1.2. Архітектурний стиль і внутрішній патерн

**Системний стиль — Modular Monolith (ADR-001).**
Система є єдиним розгортаним юнітом із чітким поділом коду на логічні модулі (Auth, Groups,
Transactions/Feed, Gift, Money Requests, Notifications, Monobank). Вибір обґрунтований трьома
аргументами: гарантована **узгодженість фінансових даних** у межах одного процесу (без
розподілених транзакцій), **мінімальний DevOps-overhead** (1 інстанс замість 5–7
мікросервісів) та **швидкість розробки** малою командою. Мікросервіси та Serverless відхилено
як надмірно складні й непередбачувані за latency для бюджетного проєкту.

**Внутрішній патерн — Layered Architecture (SAD-001).**
Багатошарова архітектура обрана замість Clean/Onion, оскільки домен переважно CRUD-орієнтований,
а інверсія залежностей через інтерфейси не дає практичної вигоди (зміна СУБД не планується).
Структура шарів backend:

| Шар | Каталог | Відповідальність |
|-----|---------|------------------|
| Presentation | `app/api/` | HTTP-роутери, маршрути, коди відповідей. Без бізнес-логіки. |
| Business Logic | `app/services/` | Сценарії використання, бізнес-правила, оркестрація. Не знає про HTTP. |
| Data Access | `app/repositories/` | CRUD над колекціями MongoDB через Motor. |
| Models | `app/models/` | Сутності (Entities) — структури документів БД. |
| Schemas (DTO) | `app/schemas/` | Pydantic-контракти вхід/вихід API; декаплінг БД ↔ API. |
| Config / Core | `app/config/`, `app/core/` | Підключення до БД, JWT-параметри, шифрування, залежності. |

**Правило залежностей (суворо зверху вниз):**
`api/ → services/ → repositories/ → MongoDB`. Роутери ніколи не імпортуються сервісами,
сервіси — репозиторіями. Це ізолює зміни: новий endpoint не зачіпає бізнес-правил, а
оптимізація запитів до БД не вимагає правок у роутерах.

### 1.3. Структура модулів і взаємодія FE ↔ BE ↔ DB

```
┌────────────────────────┐      HTTP/REST (JSON)     ┌────────────────────────┐     TCP / Motor    ┌────────────────────┐
│     Frontend (SPA)     │ ───────────────────────►  │      Backend (API)     │ ─────(async)─────► │   MongoDB Atlas    │
│                        │ ◄───────────────────────  │                        │ ◄───────────────── │                    │
│  Vue 3 + Composition   │      WebSocket (real-time)│  FastAPI + Uvicorn     │                    │ Колекції:          │
│  Vue Router            │ ◄═══════════════════════► │  Layered Architecture  │                    │ users, groups,     │
│  composables/ services │                           │  JWT (httpOnly Cookie) │                    │bank_cards,         │
│  Axios HTTP client     │                           │  Pydantic validation   │                    │transactions,       │
│                        │                           │                        │                    │gift_events,        │
│  Cloudflare Pages      │                           │  Render.com            │                    │money_requests,     │
│  (статичний бандл)     │                           │  (Docker)              │                    │notifications…      │
└────────────────────────┘                           └───────────┬────────────┘                    └────────────────────┘
                                                                 ▲
                                                     POST webhook│ (statementItem)
                                                    ┌────────────┴───────────┐
                                                    │     Monobank API       │
                                                    │   (зовнішнє джерело)   │
                                                    └────────────────────────┘
```

**Frontend** (`frontend/src/`): `views/` — 12 сторінок (Login, Register, Feed, GiftEvents,
GroupSetup, Settings та ін.); `components/` — 17 UI-компонентів; `composables/` — винесена
логіка (auth, real-time, нескінченний скрол, реакції); `services/` — клієнт API поверх Axios з
interceptor'ами; `router/`, `locales/`, `utils/`.

**Backend** (`backend/app/`): 11 роутерів у `api/` (auth, group, bank_card, transaction, feed,
gift, request, monobank, notifications, ws, health); 7 сервісів; репозиторії; 15 моделей; 8 груп
DTO-схем; middleware (JWT, CORS, rate-limiting через slowapi); міграція ініціалізації БД.

**Ключові потоки взаємодії:**
1. **Аутентифікація** — `POST /auth/login` → JWT у httpOnly Secure Cookie (SameSite=Strict).
   Backend stateless: токен містить `{user_id, email, role}`, серверних сесій немає.
2. **Підключення Monobank** — Admin передає Personal Token → backend валідує його, шифрує
   (`cryptography`) і реєструє webhook-URL у Monobank.
3. **Автоматичні транзакції** — Monobank надсилає `POST webhook` → backend перевіряє
   idempotency за `statementItem.id`, збагачує категорією (MCC → category), зберігає в
   `transactions` → **BroadcastService** надсилає подію через WebSocket усім учасникам групи.
4. **Сімейна стрічка** — `GET …/transactions` (пагінація + `$lookup` авторів) + WebSocket-канал
   для миттєвих оновлень без перезавантаження.
5. **Secret Gift Mode (killer-feature)** — ізоляція Target User на двох рівнях: API
   (`403 Forbidden` до `unlock_date`) та feed (фільтрація `is_gift_related`).
6. **Money Request** — `POST /requests` → WebSocket-подія → модальне вікно в отримувача →
   `PATCH /requests/{id}` (accept/reject) → подія назад ініціатору.

Дані між шарами передаються **виключно через DTO (Pydantic-схеми)** — сутності БД ніколи не
віддаються напряму на клієнт, що забезпечує валідацію, фільтрацію вихідних полів і декаплінг
структури БД від API-контракту.

### 3.2. Backlog (не увійшло в MVP)

| Пункт | Причина / статус |
|-------|------------------|
| **Автоматизовані frontend-тести (unit/E2E)** | UI тестувався вручну; інфраструктура (Vitest/Playwright) не налаштована. |
| **JWT refresh-endpoint** | У дизайні описаний `POST /auth/refresh`, у реалізації відсутній — наразі лише access-токен; автоматичне оновлення сесії — у Backlog. |
| **Redis Pub/Sub для broadcast** | WebSocket-стан тримається in-memory (достатньо для 1 інстансу); горизонтальне масштабування потребуватиме Redis. |
| **Формальне навантажувальне тестування** | NFR продуктивності — цільові; вимірювання p95 під навантаженням не проводилося. |
| **Винесення модуля Reports у мікросервіс** | Закладено архітектурно (Modular Monolith), але не потрібне для поточного масштабу. |
| **Звіти / аналітика витрат** | Базова агрегація є; розширена аналітика — наступна ітерація. |

### 3.3. Підсумок

MVP **Family Wallet** повністю досягнув поставленої мети: реалізовано робочий веб-застосунок
для спільного ведення сімейного бюджету з автоматичною real-time стрічкою, режимом таємних подарунків і запитами переказів. Система розгорнута в production за
≈ 14 тижнів силами команди з 4 розробників у межах безкоштовної інфраструктури.

Обрані архітектурні рішення (Modular Monolith + Layered Architecture, async-стек FastAPI/Motor,
NoSQL MongoDB) виправдали себе: вони забезпечили високу швидкість розробки, узгодженість
фінансових даних і просте розгортання, водночас залишивши чіткий шлях до масштабування.
Основні напрями подальшого розвитку — покриття frontend автотестами, повний цикл JWT-refresh та
горизонтальне масштабування real-time через Redis.
